# desk — канбан-доска для агентов

Дата: 2026-09-24
Статус: дизайн одобрен, ожидает ревью спеки

## 1. Цель

Локальная канбан-доска на уровне проекта. На ней AI-агенты (Claude Code и его сабагенты) создают и двигают задачи через MCP-сервер, а человек видит доску в браузере и тоже может с ней работать.

Человек описывает колонки, поля, правила переходов и инструкции по заполнению в одном YAML-файле. Агент получает эти инструкции через MCP и заполняет поля правильно. Сервер строго проверяет каждое действие и в ответе на ошибку объясняет, как её исправить.

### Критерии успеха

- Агент в любой сессии Claude Code создаёт задачу через MCP, и через 1 секунду или раньше она видна в открытом UI.
- Агент не может сохранить задачу с недопустимым значением поля, без обязательного поля или с запрещённым переходом. Ошибка содержит `guide` поля и допустимые значения.
- Все данные доски лежат в git в виде читаемых файлов.

### Решения, принятые на брейншторме

| Вопрос | Решение |
|---|---|
| Масштаб | Одна доска на проект |
| Хранилище | Файлы в репозитории проекта, в git |
| Описание полей | Только YAML (`board.yaml`), редактора в UI нет |
| Строгость | Строгая проверка + правила переходов + WIP-лимиты |
| Архитектура | Один пакет `desk`, две команды (`desk mcp`, `desk ui`) поверх общего ядра |

## 2. Архитектура

```
Claude Code session ──stdio──▶ desk mcp ─┐
Claude Code session ──stdio──▶ desk mcp ─┤
                                         ├──▶ core ──▶ .desk/ (board.yaml, tasks/*.md)
Browser ──HTTP/SSE──▶ desk ui ───────────┘               ▲
                         └── chokidar watch ─────────────┘
```

- `core` — чтение и проверка `board.yaml`, чтение и запись задач, проверка полей и переходов, lock, выдача ID. Не зависит от MCP и HTTP.
- `desk mcp` — MCP-сервер по stdio. Claude Code запускает отдельный процесс на каждую сессию. Постоянного процесса нет.
- `desk ui` — локальный HTTP-сервер: отдаёт собранный UI, HTTP API и SSE-поток изменений.
- Одни и те же файлы могут писать несколько процессов одновременно. Согласованность обеспечивают lock-файл и атомарная запись (раздел 4.4).

Стек: TypeScript, Node.js ≥ 20, `@modelcontextprotocol/sdk`, `zod`, `yaml`, `gray-matter`, `chokidar`, `markdown-it`. UI: Vite + React, `@dnd-kit`. Тесты: `vitest`, Playwright.

## 3. Формат данных

### 3.1 Структура папки проекта

```
.desk/
  board.yaml        # схема доски (в git)
  tasks/
    T-001.md        # одна задача = один файл (в git)
  .lock             # lock-файл (в .gitignore)
```

### 3.2 `board.yaml`

```yaml
version: 1
name: desk
id_prefix: T
guide: |
  Общие правила для агентов. Сервер отдаёт этот текст в get_board.

columns:
  - id: backlog
    title: Backlog
    guide: "Новые задачи."
  - id: in_progress
    title: In progress
    wip_limit: 3
    guide: "Берёшь задачу — ставь assignee = своё имя."
  - id: review
    title: Review
  - id: done
    title: Done

transitions:
  - from: backlog
    to: in_progress
    requires: [assignee]
  - from: in_progress
    to: review
    requires: [pr_url]
  - from: review
    to: [in_progress, done]

fields:
  - id: priority
    type: enum
    values: [p0, p1, p2, p3]
    required: true
    default: p2
    guide: "p0 — прод лежит. p1 — блокирует другую задачу. p2 — по умолчанию. p3 — nice to have."
  - id: pr_url
    type: url
    guide: "Ссылка на PR. Нужна для перехода в review."
```

Правила схемы:

- `version` — сейчас только `1`.
- `id_prefix` — латинские буквы, по умолчанию `T`.
- `columns` — минимум одна колонка. `id` уникальны и соответствуют `^[a-z][a-z0-9_]*$`. Порядок в списке задаёт порядок на доске. Первая колонка — колонка по умолчанию для новых задач. `wip_limit` — целое число > 0, необязательное.
- `transitions` — необязательная секция. Если её нет, разрешён любой переход. Если она есть, разрешены только перечисленные пары. `to` — строка или список. `from` и `to` ссылаются на существующие колонки. `requires` ссылается на пользовательские поля или на встроенное `assignee`.
- `fields` — `id` уникальны, соответствуют `^[a-z][a-z0-9_]*$` и не совпадают со встроенными полями. Типы:

| type | значение | доп. параметры |
|---|---|---|
| `string` | строка в одну строку, до 200 символов | |
| `text` | многострочная строка | |
| `number` | конечное число | `min`, `max` |
| `bool` | `true` / `false` | |
| `date` | `YYYY-MM-DD` | |
| `url` | абсолютный `http(s)://` URL | |
| `enum` | одно значение из `values` | `values` обязателен |
| `multi_enum` | массив уникальных значений из `values` | `values` обязателен |
| `task_ref` | ID существующей задачи | |

- `required` — поле обязательно всегда, при создании и при обновлении.
- `default` — подставляется при создании, если значение не передано. Должно проходить проверку типа.
- `guide` — инструкция для агента. Есть у доски, у колонок и у полей.

Любая ошибка схемы — это `INVALID_BOARD` с путём (`fields[2].values`) и номером строки YAML.

### 3.3 Файл задачи

```markdown
---
id: T-012
title: Добавить rate limit на /api/login
column: in_progress
assignee: backend-agent
created_by: planner
created_at: 2026-09-24T10:30:00Z
updated_at: 2026-09-24T11:02:00Z
priority: p1
history:
  - { at: 2026-09-24T10:30:00Z, by: planner, from: null, to: backlog }
  - { at: 2026-09-24T11:02:00Z, by: backend-agent, from: backlog, to: in_progress }
---
Описание задачи в markdown.

## Notes
- 2026-09-24T11:05:00Z · backend-agent: выбрал express-rate-limit.
```

- Встроенные поля есть всегда: `id`, `title`, `column`, `assignee` (строка или отсутствует), `created_by`, `created_at`, `updated_at`, `history`. В `board.yaml` их не объявляют.
- `title` — обязательный, 1–200 символов.
- Тело файла — описание в markdown. Раздел `## Notes` в конце тела создаётся автоматически при первом `add_note`. Описание — это всё тело до `## Notes`.
- `history` пополняется при создании (`from: null`) и при каждом переходе.
- Время хранится в UTC, в ISO 8601.

### 3.4 ID задач

- Новый ID = максимальный номер среди `tasks/*.md` + 1, с нулями до 3 цифр (`T-001`, `T-042`, `T-1000`).
- ID выдаётся под lock вместе с записью файла.
- Известное ограничение: задачи, созданные параллельно на двух git-ветках, могут получить одинаковый ID. `desk validate` и UI сообщают о дубликате, а человек переименовывает задачу руками.

### 3.5 Порядок карточек

Внутри колонки: по полю `priority`, если это `enum` (порядок значений в `values`), затем по `created_at` по возрастанию. Ручной сортировки нет.

### 3.6 Невалидные файлы

Файл задачи, который не проходит проверку (например, после ручной правки), не ломает чтение доски. `list_tasks` и UI возвращают такую задачу с признаком `invalid` и списком ошибок. Изменяющие операции над такой задачей проходят, только если результат валиден.

## 4. Ядро: проверки

### 4.1 Поля

- Неизвестное поле → `UNKNOWN_FIELD`.
- Значение не проходит проверку типа → `INVALID_VALUE`. Для `enum` и `multi_enum` в `allowed` передаётся список `values`.
- Обязательное поле отсутствует после применения изменений → `REQUIRED_MISSING`.
- Значение `null` в изменении удаляет необязательное поле.
- `task_ref` на несуществующую задачу → `INVALID_VALUE`.

### 4.2 Переходы

Для `move_task(id, to, fields)`:

1. `to` не существует → `NOT_FOUND`.
2. `to` совпадает с текущей колонкой → переход не выполняется, `history` не меняется. Если `fields` переданы, они применяются как в `update_task`. Результат — успех.
3. Пары `(from, to)` нет в `transitions`, и секция `transitions` задана → `TRANSITION_FORBIDDEN`, в `allowed` передаются колонки, куда можно перейти.
4. `fields` применяются к задаче и проверяются по 4.1.
5. Поле из `requires` пустое после применения `fields` → `TRANSITION_REQUIRES`, в `field` передаётся первое недостающее поле.
6. В `to` уже `wip_limit` задач → `WIP_LIMIT`.
7. Запись: `column`, поля, `updated_at`, новая запись в `history`.

Все проверки выполняются до записи. Если одна проверка не прошла, ничего не записывается.

### 4.3 Создание

`create_task` без `column` кладёт задачу в первую колонку. С `column` ≠ первой колонке применяются правила 4.2 для перехода из первой колонки в `column`. WIP-лимит проверяется всегда.

### 4.4 Запись и конкурентность

Каждая изменяющая операция:

1. Берёт эксклюзивный lock `.desk/.lock` (создание файла с флагом `wx`, повтор каждые 25 мс, таймаут 5 с → ошибка `LOCK_TIMEOUT`). Lock старше 30 с считается брошенным и удаляется.
2. Читает актуальные файлы с диска.
3. Проверяет операцию.
4. Пишет `T-xxx.md.tmp`, затем делает `rename` в `T-xxx.md`.
5. Снимает lock в `finally`.

Действует правило «последняя запись побеждает». Потерянных обновлений нет, потому что чтение и запись выполняются под одним lock.

### 4.5 Формат ошибок

```json
{
  "code": "TRANSITION_REQUIRES",
  "message": "Переход in_progress → review требует поле pr_url",
  "field": "pr_url",
  "guide": "Ссылка на PR. Нужна для перехода в review.",
  "allowed": null
}
```

Коды: `NOT_FOUND`, `UNKNOWN_FIELD`, `INVALID_VALUE`, `REQUIRED_MISSING`, `TRANSITION_FORBIDDEN`, `TRANSITION_REQUIRES`, `WIP_LIMIT`, `INVALID_BOARD`, `LOCK_TIMEOUT`, `BAD_REQUEST` (некорректные параметры вызова, например пустой `actor`).

`guide` заполняется, если ошибка относится к полю или колонке, у которых есть `guide`.

## 5. MCP-сервер (`desk mcp`)

### 5.1 Tools

| tool | параметры | результат |
|---|---|---|
| `get_board` | — | `name`, `guide`, колонки (`id`, `title`, `guide`, `wip_limit`, `count`), поля (`id`, `type`, `values`, `required`, `default`, `guide`), переходы |
| `list_tasks` | `column?`, `assignee?`, `query?`, `where?`, `limit?` (по умолчанию 50, максимум 200) | список `{id, title, column, assignee, fields, invalid?}` |
| `get_task` | `id` | вся задача: поля, описание, notes, history, ошибки валидности |
| `create_task` | `actor`, `title`, `description?`, `column?`, `fields?` | созданная задача |
| `update_task` | `actor`, `id`, `title?`, `description?`, `fields?` | обновлённая задача |
| `move_task` | `actor`, `id`, `to`, `fields?` | обновлённая задача |
| `add_note` | `actor`, `id`, `text` | обновлённая задача |

- `query` — поиск подстроки без учёта регистра по `title` и описанию.
- `where` — точное совпадение по полям. Для `multi_enum` значение считается совпавшим, если оно содержится в массиве.
- `update_task` не меняет `column`. Для этого есть `move_task`.
- Инструмента удаления нет.

### 5.2 `actor`

Сабагенты вызывают тот же stdio-процесс, что и родительская сессия, поэтому сервер не определяет агента сам. `actor` — обязательная непустая строка до 64 символов у всех изменяющих tools. Значение записывается в `created_by`, `history[].by` и в notes.

### 5.3 Схема в описании tools

- При старте сервер строит input schema для `fields` в `create_task`, `update_task`, `move_task` из `board.yaml`: тип каждого поля, `enum` из `values`, `description` из `guide`. Параметры `column` и `to` получают `enum` из id колонок.
- Сервер следит за `board.yaml`. После изменения сервер перечитывает файл и отправляет `notifications/tools/list_changed`. Если новый `board.yaml` невалиден, сервер оставляет прежнюю схему, а изменяющие вызовы возвращают `INVALID_BOARD`.
- Поле `instructions` сервера: «Это канбан-доска проекта. Сначала вызови get_board и следуй guide. В actor передавай своё имя агента.»

### 5.4 Ошибки в MCP

Ошибка возвращается как результат tool с `isError: true`. Содержимое — JSON из 4.5 в text content.

### 5.5 Поиск корня проекта

Сервер ищет папку `.desk/` вверх от cwd. `DESK_ROOT` задаёт корень явно. Если `.desk/` не найдена, все tools возвращают `INVALID_BOARD` с подсказкой «запусти desk init».

## 6. Веб UI (`desk ui`)

### 6.1 Сервер

- `desk ui [--port 4717] [--open]`, поиск корня как в 5.5.
- Слушает только `127.0.0.1`.
- Проверка `Host`: разрешены `127.0.0.1:<port>` и `localhost:<port>`, иначе 403. Для запросов, которые изменяют данные, заголовок `Origin` должен совпадать с адресом сервера, иначе 403. Защита от DNS rebinding и CSRF.
- `actor` для действий из UI = `git config user.name` в корне проекта. Если имени нет, `actor` = `human`.

### 6.2 HTTP API

```
GET   /api/board
GET   /api/tasks?column=&assignee=&q=
GET   /api/tasks/:id
POST  /api/tasks                  { title, description?, column?, fields? }
PATCH /api/tasks/:id              { title?, description?, fields? }
POST  /api/tasks/:id/move         { to, fields? }
POST  /api/tasks/:id/notes        { text }
GET   /api/events                 SSE
```

Ответ: `{ ok: true, data }` или `{ ok: false, error }` с ошибкой из 4.5. HTTP-статусы: 400 для ошибок проверки, 404 для `NOT_FOUND`, 409 для `WIP_LIMIT` и переходов, 503 для `LOCK_TIMEOUT`, 500 для `INVALID_BOARD`.

### 6.3 Живое обновление

`chokidar` следит за `.desk/`, с debounce 50 мс. События SSE: `task_changed {id}`, `task_removed {id}`, `board_changed`. UI перечитывает затронутые данные. Источник изменения не важен: MCP, UI, ручная правка или `git pull`.

### 6.4 Экраны

- **Доска.** Колонки в порядке `board.yaml`, счётчик `count/wip_limit` (красный при превышении). Карточка: моноширинный ID, title, бейдж `priority`, `assignee` с цветом из хэша имени, красная метка для невалидной задачи. Предупреждение о дубликатах ID.
- **Фильтры.** Поиск, `assignee`, enum-поля. Состояние хранится в query-параметрах URL.
- **Панель задачи.** Выезжает справа. Форма полей генерируется из схемы, `guide` показан как подсказка. Описание: просмотр в markdown и редактирование. Дальше notes и history.
- **Создание задачи.** Та же форма.

### 6.5 Drag-and-drop

- Во время перетаскивания колонки, куда переход запрещён, затемнены.
- Бросок в колонку, где не хватает полей из `requires`, открывает окно с этими полями и их `guide`. Сохранение отправляет `move` с `fields`.
- Отказ сервера (`TRANSITION_FORBIDDEN`, `WIP_LIMIT` и другие): карточка возвращается на место, toast показывает `message`.

### 6.6 Безопасность рендера

Описание и notes — недоверенный ввод от агентов. Markdown рендерится через `markdown-it` с `html: false`. Ссылки — только `http(s)`, с `rel="noopener noreferrer"`.

### 6.7 Визуальное направление

«Операторская консоль»: плотная сетка в Swiss-стиле, моноширинные ID и таймстемпы, цвет только со смыслом (приоритет, агент, ошибка). Цвета, шрифты и отступы задаются CSS-токенами. Светлая и тёмная темы.

## 7. CLI

| команда | что делает |
|---|---|
| `desk init [--claude-md]` | Создаёт `.desk/board.yaml` из шаблона и `.desk/tasks/`. Добавляет `.desk/.lock` в `.gitignore`. Добавляет `desk` в `.mcp.json` (сливает с существующим файлом, не перезаписывает). С флагом `--claude-md` добавляет в `CLAUDE.md` правило работы с доской. Если `.desk/` уже есть, завершается с ошибкой и ничего не меняет. |
| `desk mcp` | MCP-сервер по stdio (раздел 5). |
| `desk ui [--port] [--open]` | Веб UI (раздел 6). |
| `desk validate` | Проверяет `board.yaml`, все задачи и дубликаты ID. Печатает ошибки, при ошибках возвращает код выхода 1. |

Запись в `.mcp.json`:

```json
{ "mcpServers": { "desk": { "command": "desk", "args": ["mcp"] } } }
```

Установка: `npm i -g .` из репозитория `desk`.

## 9. Тестирование

Покрытие ≥ 80% для `src/core`, `src/mcp`, `src/http`.

- **Unit (`vitest`):** ошибки разбора `board.yaml` с путём и строкой; проверка каждого типа поля; `required`, `default`, удаление через `null`; переходы, `requires`, WIP; создание в не первую колонку; выдача ID; frontmatter round-trip без потери описания и notes; невалидные файлы задач.
- **Конкурентность:** 20 дочерних процессов параллельно вызывают `create_task`. Все ID уникальны, 20 файлов, все валидны. Параллельные `update_task` одной задачи не теряют записи в `history`. Брошенный lock удаляется.
- **MCP integration:** клиент из `@modelcontextprotocol/sdk` запускает `desk mcp` по stdio во временной папке. Проверяются все tools, JSON ошибок, `enum` в input schema, `list_changed` после правки `board.yaml`, поведение без `.desk/`.
- **HTTP integration:** все эндпоинты, коды статусов, 403 при чужом `Host` и `Origin`, события SSE после записи файла.
- **CLI:** `init` в пустой папке, слияние с существующим `.mcp.json`, отказ при существующей `.desk/`; `validate` с кодами выхода.
- **E2E (Playwright):** drag карточки; окно `requires`; возврат карточки при запрещённом переходе и WIP; живое обновление после записи файла извне; фильтры в URL. Скриншоты на 320, 768, 1024, 1440 в светлой и тёмной теме.

## 10. Вне v1

Несколько досок в проекте, редактор схемы в UI, авторизация, публикация в npm, ручная сортировка карточек, удаление задач через tools и API, вложения, архив.
